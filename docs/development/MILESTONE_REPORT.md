## Required fixes and before/after evidence

### 1. Causes

**Formatting before stale/mapping.** Before implementation, the actual blind-test command on 1.1.0 produced this group:

```text
20 of 1,606 Delivered records show Delivered in Excel export; 1,549 match. Likely a stale or lagging status.
```

The new run produces:

```text
20 status values in Excel export differ from API only in letter case ("delivered" vs "Delivered"). Likely a formatting difference.
Next step: Consider caseFold: true for this field after reviewing the raw values.
```

`formatting_difference` groups retain expected/actual and distinguish `case_only`, `whitespace_only` and `case_whitespace`. They take precedence over stale/vocabulary hints. Repeated whitespace can be accepted explicitly with `whitespaceFold: true` on a string/enum rule; the default remains false, and surrounding whitespace is already trimmed. Human summaries and charts retain the actual spelling; HTML preserves significant spaces. A supported pattern never suppresses the underlying blocking findings.

**Numeric values are not vocabularies.** The offline `3-number-as-vocabulary` repro previously reported:

```text
3 power units values in B map 1 to 2. Likely a different vocabulary for the same field.
Next step: Check the power units mapping for B.
```

It now reports:

```text
3 power units values in B are 2 where A has 1. Repeated numeric values differ between sources.
Next step: Check how power units is derived or updated in each source.
```

The group kind is `number_change`, representing an exact repeated expected/actual pair. `type: number` never enters a vocabulary or stale cause. Pair grouping was retained rather than introducing a second signed-difference grouping heuristic; field differences and totals still show exact signed deltas.

**Consistent enum changes remain neutral; enum codes are not adjectives.** Replaying the archived Iowa finding/evidence objects through the new cause builders changes:

```text
1,691 of 25,772 N carriers show Y in Company Census CSV export (active only); 23,871 match. Likely a stale or lagging hazmat flag.
```

into:

```text
1,691 of 25,772 carriers with hazmat flag N in SMS motor carrier census API (monthly) show Y in Company Census CSV export (active only); 23,871 match.
Likely a lagging update or a different definition of the field.
Next step: Compare refresh timing in both sources and the field definitions.
```

These are **offline cause replays of the owner's archived reports**, not fresh FMCSA reads or recomputed totals. Iowa has 57 numeric groups covering 731 findings; all become `number_change`. Vermont has eight numeric groups covering 47 findings. The replay writes aggregate summaries only, with no carrier names. The archived totals remain historical 1.1.0 observations. Evidence: `output/m11/fmcsa-cause-replay.json`.

The demo keeps its stale-status label and Delivered → In transit chart. Its executed UI report now says:

```text
57 of 1,833 orders with status Delivered in API show In transit in Dispatcher; 1,776 match. Likely a lagging update or a different definition of the field.
Next step: Compare refresh timing in both sources and the field definitions.
```

README explains that the planted fixture establishes the UI lag while the generic heuristic alone does not identify the wrong source. Light/dark report screenshots were regenerated and inspected. There are no article prose quotations of the old diagnosis in this checkout; the article cover assets remain unchanged.

### 2. API inputs and numeric totals

**Absent REST properties.** The original repro still returns exit 2 by default, with the page/record error now naming both opt-ins:

```text
API: REST page 1, record 2: JSONPath $.name: property name is missing; correct the field mapping or opt in with absentAsNull: true (source) or missing: null (field).
```

With `absentAsNull: true`, the actual CLI reads API=2/export=2, zero findings, exit 0. A per-field `{path: $.name, missing: null}` is covered by the CLI and adapter regressions too. An absent ancestor property propagates null; wrong shapes, wildcard cardinality, missing strict sibling mappings and missing completion metadata remain errors. A missing join key remains invalid. These opt-ins are REST-only and do not turn unreadable pages into empty data.

**Calendar dates.** The unchanged 1.1.0 date repro returned exit 1 with two invalid values. The owner also recorded `validate` exit 0 in `logiparity-issues.md`. With 1.2.0 its unchanged datetime configuration instead fails validation with exit 2 at the actual configured locations:

```text
entities[0].compare.d.format.a: Datetime date has no time in the configured format; use type: date for a calendar date
entities[0].compare.d.format.b: Datetime date has no time in the configured format; use type: date for a calendar date
```

Changing the rule to `type: date, format: {a: yyyyMMdd, b: dd-MMM-yy}` gives A=1/B=1, zero findings, exit 0. `20250107` and `07-JAN-25` normalize to `2025-01-07`. ISO days are canonical strings, independent of report zones or epoch units. The fixed `yy` window is **00–68 → 2000–2068; 69–99 → 1969–1999**, tested at both boundaries. Invalid leap dates, timestamps, incomplete dates and time/zone formats are rejected. Source `dateFormat` is the date-only fallback; explicit field/source format wins. Datetime defaults without time tokens fail validation only where actually used, without invented source-format error paths.

**Number-sum reconciliation.** Before the fix, number sums had no reconciliation object and could only say Needs review. The executed decimal fixture now reports:

```text
Number total · B: Missing rows (1): −0.4; Extra rows (1): +0.5; Value differences (3): +0.6; Unexplained remainder: 0.
All records · B · Number total: Reference: 0.7; Source value: 1.4; Difference: +0.7; Follows from: missing rows, extra rows, value differences.
```

The identity is exact: −0.4 + 0.5 + 0.6 = +0.7. Console, HTML, Markdown, JSON and JUnit expose the breakdown. Reconciliation amounts for numbers are canonical decimal strings; money/count amounts retain integer units. Additive `exactValues` preserves number totals beyond combined JavaScript-number precision; compatibility `values` numbers remain present. A regression retains `10000000000000000.1`, accounts for a missing 0.1 and displays −0.1. Ordinary aggregate findings keep numeric expected/actual when exactly representable; an exact string is used when necessary. Arithmetic is exact over canonical normalized numbers; it cannot recover precision already lost before input normalization.

Invalid keys stay uncertain, and tolerated field changes stay in the unexplained remainder. A zero remainder alone does not remove uncertainty or change failure policy. Existing money, currency/filter and count regressions remain green.

### 3. Pagination without metadata

The baseline later-page fixture emitted no warning. A short first page still fails by default; `allowShortFirstPage` still permits it. A later short/empty page still ends the read. Page/offset sources without any completion signal now attach one warning to the report. An executed CLI fixture with a full first page and short second page returned exit 0, all three records matched and one warning:

```text
API returned no total count or completion metadata; completeness is not verified. Compare rows read with a separate count request using the same filter, or configure totalPath, totalPagesPath or hasMorePath.
```

All five formats retain it. Configured total/page-count/has-more signals avoid this warning and preserve consistency checks. Cursor and Link next-pointer termination is unchanged. A source without pagination does not acquire an unrelated pagination warning. Existing demo E2E configurations now use their available `$.pagination.total`, allowing the original clean-stderr assertions to remain meaningful.
